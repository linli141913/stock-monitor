# 阶段10正式启用运行手册

## 目的与当前边界

阶段10提供的是“正式启用准备度”控制面：它把真实影子观察、阶段9质量、规则与校准版本、数据质量、性能、安全、回退和运行手册证据按模块汇总为只读状态。它不是正式任务执行器，也不会自行打开任何生产功能。

当前代码没有正式 executor、正式 job ID 或 `main.py` 接线。没有模块被正式开启；离线检查通过、测试通过或 `/private/tmp` 中生成的工件，都不能替代真实交易日、实际服务、生产性能、生产回退演练或另行授权。

三个模块独立计算、独立启用：

| 模块 | 模块含义 | 最低真实影子观察 |
|---|---|---:|
| `trendRotation` | 市场环境与行业趋势轮动 | 20 个不同有效 A 股交易日 |
| `etfObservation` | ETF 监测可用性 | 连续 5 个真实现场交易日 |
| `leaderObservation` | 三级龙头确定性观察 | 20 个不同有效 A 股交易日 |

ETF 的 20/60 日严格时点历史覆盖仍是它自身的数据证据，不能用来替代连续 5 个现场交易日；趋势和龙头的 20 日也不能相互替代。测试夹具、旧快照、同日重跑和阶段9工程完成均不增加这些天数。

## 状态与九项门

每个模块都检查以下九项门：`stage9_quality`、`rule_version`、`calibration`、`shadow_ledger`、`data_quality`、`performance`、`security`、`rollback`、`runbook`。

每份可为 `ready_to_enable` 或 `formal_enabled` 提供依据的报告，还必须带有不可变的 `radar-formal-freshness-policy-v1`。调用方必须在输入合同中显式给出三个正数秒数：报告最大年龄、普通证据最大年龄、运营检查证据最大年龄。本项目不提供“默认通过”数值，阈值必须来自已冻结的版本化运行策略；缺策略的旧输入最多得到 `not_ready`，不能被隐式补值或恢复为全绿。

有效期边界是闭区间：年龄精确等于合同中的最大值时仍有效，超过 1 微秒即失效。构建报告时，普通证据按逐条 `sourceTime` 检查；运营包的 `checkedAt` 与逐条运营证据都按专用期限检查。有效运营包会自动形成唯一 `formal_operational_checks` 证据引用，绑定合同版本、内容 SHA-256、主体与检查时间；输入不能自行伪造或重复该引用。

| 状态 | 操作含义 |
|---|---|
| `collecting` | 真实证据仍在积累，停止启用动作。 |
| `not_ready` | 已知证据不足或未达到门槛，停止启用动作。 |
| `failed` | 证据损坏、时间异常、哈希不符或某门失败，保持关闭并先定位原因。 |
| `ready_to_enable` | 自动证据门已就绪，但仍未正式开启；必须停在这里，等待独立的生产授权。 |
| `formal_enabled` | 仅当九门通过、该模块的生产请求与有效配置均为真、且后续授权的正式执行链已实际接入时才可使用。 |

页面和 API 都是只读的。用户不审批某只股票；系统自动判断证据是否满足门槛。用户只在涉及生产配置、服务重载、部署、数据库迁移或回退等高风险动作时决定是否授权。

## 只读检查

以下命令不改变服务生命周期；仍应在项目根目录执行，并记录输出中的失败原因。

```bash
ops/launchd/manage.sh validate
ops/launchd/manage.sh status
ops/launchd/manage.sh preflight
```

- `validate`：静态校验 LaunchAgent 资产、脚本和 ngrok 配置文件格式。
- `status`：只读展示 FastAPI、ngrok LaunchAgent、8001 和 ngrok 4040 三信号。只有三信号均为 `1` 才显示 `running|identity_verified`；信号不一致是 `degraded|identity_unverified`，不能据此启用任何模块。
- `preflight`：安装前检查。若同名 LaunchAgent 已经加载而返回拒绝，这是防止重复安装的预期保护，不是需要靠重启解决的错误。

读取阶段10当前结果使用：

```text
GET /api/radar/formal-readiness
```

接口仅从内容寻址证据仓读取，并使用 `no-store`；缺失报告返回 `not_ready`，损坏、篡改、未来时间、时钟无法验证或任一寿命超限返回 `failed`。API每次读取都重验；调度守卫在注册和每次连续执行前也复用同一纯函数，所以曾经全绿但已过期的报告不会继续放行。它不读取 SQLite、不触发行情、AI 或任务执行。

## 离线演练命令

以下命令用于显式隔离目录中的合同演练，不读取环境变量、SQLite、网络或本地服务，也不启用生产功能。输入、输出和影子台账目录必须彼此隔离且全部位于经规范化的 `/private/tmp`；macOS `/tmp` 只在系统确认两者是同一目录时接受。项目目录、`backend/data`、目录重叠、符号链接和读取期间换件都失败关闭。

```bash
cd backend
./venv/bin/python run_radar_formal_shadow_observation.py \
  --module trendRotation \
  --input-dir /private/tmp/<当日趋势影子输入目录> \
  --ledger-dir /private/tmp/<阶段10影子台账仓> \
  --evaluated-at 2026-09-07T10:30:00+08:00

./venv/bin/python run_radar_formal_readiness.py \
  --input-dir /private/tmp/<正式就绪输入目录> \
  --output-dir /private/tmp/<正式就绪输出目录> \
  --shadow-ledger-dir /private/tmp/<阶段10影子台账仓>

./venv/bin/python run_radar_formal_operational_checks.py \
  --input-dir /private/tmp/<运维检查输入目录> \
  --output-dir /private/tmp/<运维检查输出目录>
```

影子采集命令按模块读取固定版本的运行回执、主来源工件、外部新鲜度策略、官方日历封套和上交所原始HTML；趋势模块还必须提供行业快照，且阶段6主来源工件必须原生包含完整 `radar-market-feature-snapshot-evidence-v1`。采集器会重算快照哈希、重建 `MarketFeatureSnapshot`、调用冻结默认策略重算状态，再与工件的市场状态逐字段比较。ETF模块还必须提供只用于产品身份的正式准入包。它不联网、不自行产生回执，同模块同一上海交易日只允许内容完全相同的幂等重放。正式就绪命令只有从显式 `--shadow-ledger-dir` 重放成功时才能让影子门就绪；输入JSON中自报的台账、日期或哈希不能自证通过。

正式就绪命令只读取输入目录固定文件 `radar-formal-readiness-input-v1.json`，其外层合同必须是 `radar-formal-readiness-input-v1`；该输入若要产生可启用状态，必须显式携带上述有效期策略，CLI不会填充默认秒数。运营检查命令只读取 `radar-formal-operational-checks-input-v1.json`，输出 `radar-formal-operational-checks-v1.json`。三个入口遇到路径重叠、符号链接、生产数据目录或合同/哈希异常都必须失败关闭。不要把临时输出复制进生产证据仓，也不要以手工 JSON、环境变量编辑或页面操作作为启用路径。

## 真实交易日单次采集与登记

以下入口已经接通，但只能在有效 A 股交易日的合法采集窗口使用真实当轮数据。它们仍只写 `/private/tmp`，不读写生产 SQLite，不接 `main.py` 或生产调度，也不会开启正式状态。路径中的日期、前态、准入包和时间必须替换为当轮真实值，不能沿用示例值。

阶段6五源入口可在原验收完成的同一进程内，额外发布趋势和龙头的强类型回执及原子输入目录：

```bash
cd backend
PYTHONPYCACHEPREFIX=/private/tmp/codex-stage10-live-pycache \
  ./venv/bin/python run_leader_phase6_live_five_source_acceptance.py \
  --confirm-live-five-source \
  --output-dir /private/tmp/<阶段6当轮输出目录> \
  --previous-sector-state /private/tmp/<上一顺序行业状态.json> \
  --formal-shadow-input-root /private/tmp/<当日阶段10输入根>
```

只有输出中的 `formalShadowInputPublishStatus=published` 才继续。随后分别使用输出里的真实 `formalShadowInputDirs.trendRotation` 和 `formalShadowInputDirs.leaderObservation` 登记；`evaluated-at` 必须是当轮完成后的真实上海时间：

```bash
./venv/bin/python run_radar_formal_shadow_observation.py \
  --module trendRotation \
  --input-dir /private/tmp/<输出返回的趋势目录> \
  --ledger-dir /private/tmp/<阶段10真实影子台账仓> \
  --evaluated-at <真实ISO-8601上海时间>

./venv/bin/python run_radar_formal_shadow_observation.py \
  --module leaderObservation \
  --input-dir /private/tmp/<输出返回的龙头目录> \
  --ledger-dir /private/tmp/<阶段10真实影子台账仓> \
  --evaluated-at <真实ISO-8601上海时间>
```

ETF 使用独立的一次性入口：显式证券集合只请求腾讯行情一次，再把捕获、同日 ETF 身份准入、官方日历和冻结策略原子发布并登记到同一台账。日历与策略可直接取当日已发布的趋势输入目录；ETF 准入必须是同日独立生成且自身校验通过的 `radar-etf-formal-admission-v2.json`，不得拿旧准入包或排名结果代替现场观察。

```bash
./venv/bin/python run_radar_etf_live_shadow_capture.py \
  --confirm-live-etf-shadow \
  --symbols <当轮ETF代码> \
  --run-id <当轮唯一运行ID> \
  --admission-file /private/tmp/<当日ETF准入包.json> \
  --calendar-envelope-file /private/tmp/<趋势目录>/radar-formal-shadow-calendar-input-v1.json \
  --calendar-document-file /private/tmp/<趋势目录>/sse-official-calendar.html \
  --collection-policy-file /private/tmp/<趋势目录>/radar-formal-shadow-collection-policy-v1.json \
  --output-root /private/tmp/<当日ETF输入根> \
  --ledger-dir /private/tmp/<阶段10真实影子台账仓>
```

首次真实内容应返回 `available`，完全相同内容的幂等重放返回 `unchanged`；捕获锁竞争返回 `contended`，且不请求行情、不发布输入、不登记失败日。`failed`、`missing`、`stale`、来源健康异常或任一合同不一致都不能计为就绪观察日。同模块同一上海交易日的不同内容不得覆盖已有记录。

## 统一单次协调与运营证据

阶段10已经提供单次协调入口，用于在一个冻结调度时隙中依次执行阶段9、趋势登记、龙头登记和ETF捕获登记。它只在已确认、有效A股交易日且处于连续竞价窗口时运行；周末、盘前、午休、收盘后或官方日历无法验证时，不构造真实入口、不创建采集目录，也不请求网络。

协调入口不接受手工填写的调度时间。运行前先准备一个权限为0700的 `/private/tmp/<冻结调度输入目录>`：固定主文件名为 `schedule-input.json`，其中引用同目录内的上交所日历封套和原始HTML，并声明版本化策略、有效交易日、时隙、生效窗口及固定四模块范围；所有文件权限为0600。对 `schedule-input.json` 原始字节计算 SHA-256 后，使用下列入口发布内容寻址调度仓：

```bash
cd backend
./venv/bin/python run_radar_stage10_frozen_schedule.py \
  --input-dir /private/tmp/<冻结调度输入目录> \
  --input-sha256 <schedule-input.json原始字节SHA-256> \
  --output-store-root /private/tmp/<冻结调度仓>
```

入口会严格拒绝重复JSON键、非有限数、非法UTF-8、超限文件、路径或祖先符号链接、读取期间换件、输入哈希不符、休市日期和无法由官方原文重算的交易日。发布成功后再用正式 loader 回读，输出 `manifestSha256` 以及一个或多个 `slotId`，不输出本地绝对路径。取得这两个不可变身份后再运行单次协调器；每个时隙由官方日历、版本化策略、生效窗口和固定四模块范围共同绑定。命令形态如下，所有目录仍必须位于 `/private/tmp`，参数必须替换为当轮真实值：

```bash
cd backend
PYTHONPYCACHEPREFIX=/private/tmp/codex-stage10-live-pycache \
  ./venv/bin/python run_radar_stage10_single_live_collection.py \
  --confirm-live-stage10-collection \
  --attempt-root /private/tmp/<当轮attempt根> \
  --attempt-id <当轮唯一attempt-id> \
  --schedule-store-root /private/tmp/<冻结调度仓> \
  --schedule-manifest-sha256 <冻结调度清单SHA-256> \
  --slot-id <冻结时隙ID> \
  --attempt-universe-root /private/tmp/<实际调用全集仓> \
  --campaign-dir /private/tmp/<阶段9正式活动仓> \
  --stage6-output-dir /private/tmp/<阶段6当轮输出目录> \
  --cohort-output-dir /private/tmp/<阶段9当轮cohort目录> \
  --formal-shadow-input-root /private/tmp/<趋势和龙头输入根> \
  --previous-sector-state /private/tmp/<上一顺序行业状态.json> \
  --cninfo-pdf-cache-dir /private/tmp/<巨潮PDF缓存> \
  --formal-etf <当轮ETF代码> \
  --ledger-dir /private/tmp/<阶段10真实影子台账仓> \
  --etf-output-root /private/tmp/<当轮ETF输入根>
```

协调器会在任何外部来源调用前发布不可变 `pending` 检查点和实际调用全集条目，完成后只原子升级同一条记录。进程中断、最后发布失败、同一时隙重复调用或锁竞争都不能把 invocation 隐藏；恢复时按固定检查点 SHA-256 重放尚未完成的登记，不重复已完成的阶段9或行情请求。只有命令最终返回成功，且检查点与 attempt-universe 均可从内容寻址仓重新加载，才可进入运营证据汇总。

运营证据采集入口为：

```bash
cd backend
./venv/bin/python run_radar_formal_operational_evidence_collector.py \
  --input-dir /private/tmp/<运营采集输入内容仓> \
  --output-dir /private/tmp/<运营证据输出目录> \
  --asset-root /private/tmp/<冻结运营资产根>
```

正式采集输入必须绑定冻结调度、完整 attempt-universe、每次不可变检查点、相应历史影子台账版本及性能、安全、回退和手册策略。旧手工输入只能得到 `rehearsal/collecting`；缺少 invocation、存在 `pending`、重复成功、台账版本链不单调、策略或资产哈希不符时均不能通过。正式就绪构建器还会从固定临时根与固定项目资产根重新执行收集器，并要求重算报告与提交报告完全一致，因此不得手工复制或编辑一份全绿运营报告。

当前正式执行部分仍是默认关闭的暗骨架：没有真实 executor、binding、正式 job 实例或 `main.py`/launchd/AI 接线。它只能验证未来接线时的任务身份、证据有效期、跨进程互斥和结果合同；不得把本地报告、命令成功或页面显示解释为已经正式启用。

## 真实证据与授权顺序

1. 在合法交易日按既有影子链积累各模块自己的真实观察日，并保留来源时间、抓取时间、覆盖率、缺失、失败、过期和锁状态。
2. 按阶段9真实前向序列积累 development、calibration、holdout 及每个样本日后的 5 个已收盘交易日；只有内容校验后的真实质量报告才能满足对应模块的阶段9门。
3. 冻结规则、阈值和校准版本；补齐可复核的数据质量、性能、安全、回退和手册证据。性能阈值必须来自版本化策略，未冻结时保持 `collecting`，不能临时填数放行。
4. 由只读 API 核对该模块为 `ready_to_enable`，并核对其他模块不会被错误代替。
5. 单独取得生产授权后，才设计并复核真实 executor、正式任务 ID、服务端请求配置、有效开关和受控服务变更。当前阶段没有这条执行链，不能跳过此项。
6. 授权后的发布/重载后，再以实际服务、健康状态和模块证据复核；任一门失效、证据过期或服务异常，撤销受影响模块的正式状态并保留影子观察。

## 失败、停止与回退边界

- `collecting`、`not_ready` 或 `failed`：停止启用，不用旧报告、Fixture、AI、同日重复运行或其他模块结果补齐。
- `ready_to_enable`：只表示证据就绪，不表示配置已改、服务已加载或任务存在。没有独立授权时停止。
- 事件只影响某个模块时，只撤销该模块；`ops/launchd/manage.sh disable-radar` 是整套雷达影子配置的生命周期命令，不是单模块正式回退按钮。
- `reload-backend`、`enable-radar`、`disable-radar`、安装、卸载和部署都会改变本机或线上状态，必须另行授权。阶段10的只读控制面不执行这些命令。
- 若涉及生产 SQLite，先取得独立授权，再完成一致性备份、SHA-256、完整性检查和已验证的恢复路径。不得用删除数据、覆盖现库或无校验备份作为回退；本阶段既不读写生产 SQLite，也不提供数据库回退脚本。

## 记录要求

每次真实验收或授权变更都应记录：模块、版本、`checkedAt`、证据 SHA-256、观察日数量、九门状态、实际请求/配置/正式状态、服务健康与是否发生授权动作。只要任一项无法验证，就记录缺失或失败，不把浏览器渲染时间当作来源时间。
