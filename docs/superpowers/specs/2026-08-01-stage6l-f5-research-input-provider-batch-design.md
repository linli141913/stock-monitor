# 阶段 6L-F5 研究输入提供器批次设计

## 目标

冻结同一雷达运行、统一时点和完整候选集合下的历史、主营催化、可交易性
输入及E3风险批次，形成只读强类型交付合同。F5只验证和编排已有对象，不
抓取来源、不计算研究特征，也不接入生产运行时。

## 同轮身份

`LeaderRuntimeAssembly`与每个研究组件显式携带`radar_run_id`、行情
`quote_batch_id`和行情来源合同ID。组件集合ID同时绑定这些字段、证券、
时点、行业及行业发布ID，防止跨轮、跨行情批次或跨行业拼接。

Assembly中的有序候选是唯一权威集合。提供器条目允许不同输入顺序，但
证券集合必须完全一致且无重复，结果必须恢复Assembly顺序；不得通过三个
稀疏映射或E3 ready投影的交集反推候选。

## 输入语义

每个候选都必须有显式提供器条目：

- `None`表示该类来源已明确缺失，候选保留为`partial`；
- 非`None`对象必须是对应强类型输入，并与候选证券、统一时点、行业、行业
  发布ID或行情来源合同一致；
- 类型、身份或时点错配只阻断该候选，并从所有可消费映射排除；
- E3必须是覆盖完整候选集合的合法批次。非ready条目保留缺失语义，条目
  缺席、重复或额外证券属于整批合同错误。

结果使用冻结dataclass、tuple及只读mapping proxy，不在`repr`或压缩证据中
泄露原始历史序列、披露正文或人工审核内容。

## 零重算边界

新增纯函数`attach_leader_risk_candidate_projections()`，只替换既有
Assembly中的`researchFeatures.riskCandidateProjection`。F4先把合法E3
投影挂到同一个Assembly，再组装F2并回挂F3；五类研究特征构造器调用次数
保持为零，原Assembly保持不变。

## 明确不做

- 不修改`backend/radar/runtime.py`，不接仓储、SQLite、迁移、调度、API或页面；
- 不实现历史、主营催化、可交易性或风险来源抓取器；
- 不通过先构建一次候选、再带来源输入第二次构建Assembly来实现生产编排；
- 不启用正式行业门槛、股票硬门槛、风险过滤、评分或状态迁移；
- 不新增依赖、环境变量或开关，不停止或重启服务，不执行Git或部署操作。

## 后续边界

F6应先建立“两阶段候选计划”：第一阶段只冻结候选身份和同轮来源合同，
第二阶段批量获取所有候选的研究输入并单次生成Assembly、E3、F2和F3。
在该单遍编排通过临时环境验证前，不接默认关闭的阶段6影子运行时。

## 验收

1. run、asOf、行情批次、来源合同和候选集合均被稳定校验；
2. ready、显式缺失、单股错配和整批错误语义分开；
3. E3完整非ready条目不被过滤或补造；
4. 三类输入映射只读，原始对象不进入压缩证据；
5. F4风险挂接和研究审计全过程不重算五类特征；
6. 所有正式标志严格关闭，分层与完整后端回归通过。
